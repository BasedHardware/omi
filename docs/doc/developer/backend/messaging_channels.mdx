## Overview

Telegram, iMessage, and SMS are thin adapters over the existing Omi core chat. Inbound messages are stored as external chat messages, sent through the normal retrieval and quota path, and returned through the originating provider.

The app remains the account authority. A channel never creates an Omi account from an inbound message and never receives a Firebase credential.

## Authentication model

1. The signed-in app authenticates with its existing Firebase ID token. The backend resolves the canonical Firebase UID for every app request.
2. The core chat issues a 48-character, single-use link code for Telegram, iMessage, or SMS. The code expires after 15 minutes and only its SHA-256 hash is stored.
3. The user proves possession of the channel by sending the code to the provider. The webhook consumes the code transactionally and binds the provider identity to the Firebase UID.
4. Webhook requests authenticate with provider credentials: Telegram's secret-token header, Sendblue's secret header plus a high-entropy path token, or Twilio's signed SMS request.
5. Users can ask the core chat for status or unlink a channel. Unlinking revokes the binding and does not delete the Omi account.

This keeps the trust boundary simple: Firebase authenticates the account, a one-time possession code authenticates the channel, and provider webhook secrets authenticate the transport.

If an unlinked user sends the first message, Omi returns a one-time sign-in URL containing a claim code. After Firebase sign-in, the web settings page consumes that code and binds the original provider identity. The manual `/start CODE` flow remains available for clients that do not open links.

## Phone registration through core chat

The `start_phone_verification` core-chat action reuses the existing caller-ID verification flow. The user explicitly supplies an E.164 number, Omi places the verification call, and the existing app verification screen completes registration. The core chat never asks for or accepts the verification code.

This is preferable to treating an SMS or call code as a chat password. It preserves the current phone ownership proof, avoids putting a reusable credential in a third-party channel, and keeps the phone number attached to the Firebase UID that started the flow.

## HTTP surfaces

| Method | Path | Authentication | Purpose |
| --- | --- | --- | --- |
| POST | `/v1/channels/{channel}/link` | Firebase ID token | Issue a Telegram, iMessage, or SMS link code |
| POST | `/v1/channels/{channel}/claim` | Firebase ID token | Consume a first-message sign-in claim code |
| GET | `/v1/channels` | Firebase ID token | List linked channels and phone-registration status |
| DELETE | `/v1/channels/{channel}` | Firebase ID token | Revoke a channel binding |
| POST | `/v1/webhooks/telegram` | Telegram secret-token header | Receive one-to-one Telegram messages |
| POST | `/v1/webhooks/sendblue/{path_token}` | Sendblue secret header and path token | Receive one-to-one iMessage messages |
| POST | `/v1/webhooks/twilio/sms` | Twilio signature | Receive one-to-one SMS messages |

Provider webhook setup is deployment configuration. The Telegram bot must point at `/v1/webhooks/telegram`; Sendblue must point at the path-token URL and send `sb-signing-secret`; Twilio must point the SMS-capable `TWILIO_SMS_NUMBER` messaging webhook at `/v1/webhooks/twilio/sms`.

## Delivery and failure behavior

Webhook events are claimed by provider event ID before processing. Duplicate events do not create another core-chat turn; a previously prepared reply may be redelivered. Replies are plain text and capped at Telegram's 4096-character limit, iMessage's 2000-character limit, or SMS's 1600-character limit.

Each linked channel invokes `execute_chat_stream` with the normal ordered core-tool registry and deferred per-user app tools. This covers the text core-chat path, including retrieval, memories, actions, calendar, mail, channel management, phone verification, screen activity, and URL fetching. Provider transports do not currently provide file/media uploads, audio, or streamed partial replies.

Local tests use fake Firestore and HTTP clients. A live acceptance check still needs deployed provider secrets, provider webhook registration, a Firebase-authenticated account, and one real inbound/outbound turn for each channel.
