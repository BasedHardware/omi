# Native recording journal

Android and Apple use native encrypted recording logs. React Native owns capture ordering and upload scheduling; native code owns keys, filesystem durability, persisted login identity and trusted ownership receipts. Browser capture has no journal bridge.

Before connection, the native adapter requests `GET /v1/device-sessions/ownership`. A successful portable response binds an opaque owner key to the canonical account and account epoch. It is retained inside the existing encrypted native session together with its configured backend origin and login generation. Token refresh preserves that generation; explicit sign-in creates a new one. Only classified DNS, connection-unavailable or timeout failures permit the exact cached origin/login binding. HTTP denial, successful owner changes, TLS errors and cancellation cannot select that cache. First use without a trusted receipt requires connectivity.

Each capture receives a native UUID and an encrypted metadata record containing the device, codec and optional `capturedAtMs`. The journal partition includes backend origin, owner key and persisted login generation. Every encrypted entry also includes the capture binding and monotonically increasing sequence. Android uses AES-GCM with an Android Keystore key. Apple uses Security.framework ECIES variable-IV X9.63 SHA-256 AES-GCM with a persistent Keychain key. Entries and directory changes are synchronized before acknowledgement. Restart recovery trims an incomplete, unacknowledged tail; authenticated-frame corruption or an incorrect key/binding fails without replacing saved audio. This provides record authentication, not a hardware anti-rollback guarantee against a compromised operating system.

The ownership receipt and keys never cross the JavaScript bridge. A journal request can open only its persisted capture/device/codec tuple and exact optional `capturedAtMs`, including absence. The server open response must preserve that timestamp before native code records the session acknowledgement. Subsequent paths must identify the server session acknowledged in that journal; the native adapter persists that acknowledgement before resolving JavaScript. Every journal request obtains fresh authenticated ownership and compares the original origin, login and owner key. A changed owner retires the handle and retains its files. A rotated signature can be replaced only for the same owner key. Server authorization and original capture epoch checks still apply independently.

Apple and Android sample native wall-clock Unix milliseconds at receipt of each nonempty BLE audio notification. React Native selects the first accepted packet for a new capture, including the packet that starts a rollover, and stores its optional `capturedAtMs` once in the encrypted tag-1 metadata. Descriptors and replay preserve that value. Native validation rejects booleans, nonnumeric, fractional, nonfinite and out-of-range values; the allowed range is 0 through 8,640,000,000,000,000 inclusive. Legacy journals with no field remain without it. This is host receipt-time provenance, not the wearable RTC, a stop timestamp, an ordering authority or billable duration. Journal creation, file modification and replay time never supply a missing value.

React Native persists packets before sending them. Upload batches contain up to 128 original BLE packets, consecutive indexes and at most 1 MiB raw audio. An in-flight batch stays unchanged across bounded retries; its packets are removed from the pending queue only after the server acknowledgement and durable local acknowledgement. A lost open or upload acknowledgement can therefore replay the same capture and packet indexes. Completion follows the full durable packet drain. Completed recordings retain their journal until transcription returns or fails, then local recovery data is removed. Unconfirmed completion retains the journal.

Upload retries exhausted while offline pause networking while durable capture continues. Reopening the app online replays retained recordings. A journal write failure stops capture visibly. Limits are 8 MiB raw audio and 65,536 packets per capture, 8 MiB pending raw audio across active captures, 32 MiB per encrypted file, 64 files and 128 MiB across all native journal partitions. Listing returns metadata only; recovery reads one journal at a time. These bounds stop capture rather than delete unacknowledged audio. Continuous recording opens a new independent session at a sequence-contiguous fragment-zero boundary when fewer than one maximum frame remains (62,208 raw bytes including headers, or 256 packet slots). The preceding session drains independently; firmware packet headers remain unchanged. A gap at the boundary is retained in the original session so transcription can reject missing audio. Rollover does not increase the global pending-memory or native disk budgets; offline exhaustion still stops capture visibly.

Historical session/transcript GET requests use normal current-account authorization. Portable mutations require ownership receipts. The Worker explicitly reports `capture_ownership_unavailable`; native journal capture does not fall back to its storage. Only the existing generic transcript retry operation may use that exact capability response to call the Worker's existing authenticated transcription route. Network failures and other responses do not select this path.

Verification runs through `scripts/test-android-http`, `scripts/test-apple-auth` and the React Native test runner. The native tests exercise real encryption, tampering, exclusive locks, child-process termination during an incomplete append and restart recovery. Apple additionally exercises an isolated real Keychain key, persisted native session acknowledgement, owner/login separation and constrained paths. Capture-time tests cover legacy absence, encrypted reopen, timestamp bounds and request/acknowledgement mismatch without changing the saved session; Android exercises the production timestamp validation policy. The capture-time native suite and all three Debug builds passed (`/tmp/v5-capture-time-native.log`, `/tmp/v5-capture-time-{ios,macos,android}-build.log`). Hook tests cover ownership preflight, fsync before upload/completion, acknowledgement loss, offline continuation and storage failure while networking is paused. Debug builds cover Android, iOS and macOS. Physical wearable capture, screen-lock event delivery, Android Keystore instrumentation and device-level process-death recovery still require actual-device evidence; a foreground service or Bluetooth background declaration alone does not prove packet delivery to React Native.

The device panel can show one remembered Omi shortcut from the current native login and canonical owner. Loading the shortcut never scans or connects. An explicit connection is remembered only after native audio readiness; Reconnect rechecks current native ownership before entering the existing recording preflight and connection flow. Forget removes the shortcut without disconnecting an active recording or deleting its journals. A new login or sign-out clears the preference; token refresh preserves it. Remembered-device lookup and reconnect require current online ownership verification.
