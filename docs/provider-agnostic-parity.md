# Provider-independent app parity

Working acceptance checklist, inspected 2026-09-07 at `df1fff16ff` plus the current working tree. This records source-backed capability boundaries. It is not a production-readiness certificate or a live deployment report. Update evidence against the deployed revision before checking an acceptance item.

## Scope and decisions to preserve

- Keep one React Native product UI and lifecycle owner across mobile, desktop and web. Credentials and authenticated transport remain native; the PWA development proxy injects credentials outside browser code. Do not copy the legacy Flutter or Swift product tree. Authority: [AGENTS.md](../AGENTS.md).
- Keep ratified memory projections and completeness semantics. Ready renders are not editable legacy memory records; missing accepted-work or short-term-memory coverage must remain visible. Do not manufacture empty successful projections to satisfy screens. Authority: [ratified contract guide](../packages/contracts/ratified/README.md).
- Keep task account epochs, revision checks, idempotent operation identities, retained uncertain writes and authoritative refresh. The UI does not optimistically claim completion. Authority: [task contract](../packages/contracts/src/domain/tasks.ts), [mutation client](../react-native/src/taskMutationClient.ts), [task UI](../react-native/src/ui/TaskEditor.tsx).
- Keep explicit setup disclosure separate from native sign-in. The old auth-only completion flag is not setup consent. Device connection is optional; no-device users can use chat. Authority: [onboarding owner](../react-native/src/app/useOnboarding.ts).
- The Cloudflare Worker is an existing implemented provider, not a provider-independent implementation merely because its HTTP shell also mounts in Elysia. Its persistence and generation implementation uses D1, R2 and Durable Objects. Authority: [Worker HTTP core](../apps/backend-worker/src/http-core.ts).
- A local seeded QA composition is an integration harness, not a production account/grant source. A first deployed memory-read slice does not complete app parity. Authority: [local entry](../backends/example-platform/apps/service/bin/dev-server.ts), [production entry](../backends/example-platform/apps/service/bin/production-server.ts).

## Current composition boundaries

**App:** [AppOrchestrator](../react-native/src/app/AppOrchestrator.tsx) coordinates shared screens, setup, reads, recording and writes. Apple and Android native transports select the rewritten backend for capture/chat/conversations/memories/tasks/settings routes; legacy account and connector APIs still use the primary cloud path. See [native path policy](../react-native/src/v5BackendOrigin.ts), [Android policy](../react-native/android/app/src/main/java/com/rnruntime/OmiBackendTransport.java) and [PWA proxy policy](../react-native/src/local-proxy.ts). The example-platform development selector currently allows conversation/memory/task reads and task operations only. It does not expose every route present in the local service.

**Worker:** [registered routes](../apps/backend-worker/src/http-core.ts) implement chat admission/history/SSE/cancellation, attachments, indexed recording upload/transcription, conversation reads and service settings. Canonical memories and task mutations require an optional authenticated service binding. Local D1 tasks can be read without that binding; that is not proof of canonical production writes.

**Local portable service:** [app-facing composition](../backends/example-platform/apps/service/app-facing.ts) mounts memories, conversations, tasks, settings, chat, listen, and additional development routes. [dev-server](../backends/example-platform/apps/service/bin/dev-server.ts) builds SQLite stores with a development principal and seeded state. Existing route logic is reusable, but its principal/control/storage composition cannot be promoted unchanged to production.

**Production entry:** [production-server](../backends/example-platform/apps/service/bin/production-server.ts), built by the [Dockerfile](../backends/example-platform/Dockerfile), composes Firebase authorization and PostgreSQL memory reads. It explicitly returns unavailable for MCP, supplies unavailable accepted-work/STM coverage, rejects rendering trees over 16 nodes and limits concurrent non-health requests to two. It does not mount the full app-facing route set. The [GCP configuration](../backends/example-platform/deploy/gcp/dev/main.tf) targets a development project; configuration existing in the tree does not prove successful rollout, grants or authenticated app access.

## Acceptance checklist for subsequent work

- [ ] **Production authority:** provision and verify real Firebase credential binding, application grant, account control and revocation for an intended account; no seeded principal or staging-token substitution.
- [ ] **Full deployed composition:** mount every required app capability above with production stores, model/storage ports and bounded shutdown/readiness behavior. Keep unsupported routes explicit until implemented.
- [ ] **Provider independence:** run the same app contract scenarios against Worker and portable production composition. Where the app wire differs (`/v1/device-sessions` versus `/v4/listen`), implement the accepted boundary rather than silently switching semantics.
- [ ] **Real mobile path:** fresh setup → sign-in → optional device → recording/transcript → conversation → task mutation → Settings/Apps, with reload and account isolation. Simulator rendering alone does not close physical-device checks.
- [ ] **Failure and recovery:** credential expiration/revocation, offline/process death, interrupted uploads, uncertain writes, SSE reconnect/cancel, stale task revision/epoch and unavailable projections produce the intended recoverable state.
- [ ] **Production release evidence:** record deployed revision/configuration, account-scoped end-to-end results, migration/rollback readiness and provider-specific resource verification. Health/ready 200 and a container image are prerequisites, not full parity.

Existing local evidence and limitations live in [production-readiness.md](production-readiness.md). This checklist adds no new domain authority, seeded production data, or declaration that all capabilities are complete.
