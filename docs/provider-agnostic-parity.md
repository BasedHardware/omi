# Provider-independent app parity

Working acceptance checklist, inspected 2026-09-07 against the current v5 working tree. This records source-backed capability boundaries. It is not a production-readiness certificate or a live deployment report. Update evidence against the deployed revision before checking an acceptance item.

## Scope and decisions to preserve

- Keep one React Native product UI and lifecycle owner across mobile, desktop and web. Credentials and authenticated transport remain native; the PWA development proxy injects credentials outside browser code. Do not copy the legacy Flutter or Swift product tree. Authority: [AGENTS.md](../AGENTS.md).
- Keep ratified memory projections and completeness semantics. Ready renders are not editable legacy memory records; missing accepted-work or short-term-memory coverage must remain visible. Do not manufacture empty successful projections to satisfy screens. Authority: [ratified contract guide](../packages/contracts/ratified/README.md).
- Keep task account epochs, revision checks, idempotent operation identities, retained uncertain writes and authoritative refresh. The UI does not optimistically claim completion. Authority: [task contract](../packages/contracts/src/domain/tasks.ts), [mutation client](../react-native/src/taskMutationClient.ts), [task UI](../react-native/src/ui/TaskEditor.tsx).
- Keep explicit setup disclosure separate from native sign-in. The old auth-only completion flag is not setup consent. Device connection is optional; no-device users can use chat. Authority: [onboarding owner](../react-native/src/app/useOnboarding.ts).
- The Cloudflare Worker is an existing implemented provider, not a provider-independent implementation merely because its HTTP shell also mounts in Elysia. Its persistence and generation implementation uses D1, R2 and Durable Objects. Authority: [Worker HTTP core](../apps/backend-worker/src/http-core.ts).
- A local seeded QA composition is an integration harness, not a production account/grant source. A first deployed memory-read slice does not complete app parity. Authority: [local entry](../backends/example-platform/apps/service/bin/dev-server.ts), [production entry](../backends/example-platform/apps/service/bin/production-server.ts).

## Current composition boundaries

**App:** [AppOrchestrator](../react-native/src/app/AppOrchestrator.tsx) coordinates shared screens, setup, reads, recording and writes. Apple and Android native transports select the rewritten backend for capture/chat/conversations/memories/tasks/settings routes; legacy account and connector APIs still use the primary cloud path. See [native path policy](../react-native/src/v5BackendOrigin.ts), [Android policy](../react-native/android/app/src/main/java/com/rnruntime/OmiBackendTransport.java) and [PWA proxy policy](../react-native/src/local-proxy.ts). The example-platform development selector currently allows conversation/memory/task/settings reads and task operations. It does not expose every route present in the local service.

**Worker:** [registered routes](../apps/backend-worker/src/http-core.ts) implement chat admission/history/SSE/cancellation, attachments, indexed recording upload/transcription, conversation reads and service settings. Canonical memories and task mutations require an optional authenticated service binding. Local D1 tasks can be read without that binding; that is not proof of canonical production writes.

**Local portable service:** [app-facing composition](../backends/example-platform/apps/service/app-facing.ts) mounts memories, conversations, tasks, settings, chat, listen, and additional development routes. [dev-server](../backends/example-platform/apps/service/bin/dev-server.ts) builds SQLite stores with a development principal and seeded state. Existing route logic is reusable, but its principal/control/storage composition cannot be promoted unchanged to production.

**Production entry:** [production-server](../backends/example-platform/apps/service/bin/production-server.ts), built by the [Dockerfile](../backends/example-platform/Dockerfile), composes Firebase authorization with PostgreSQL memory reads, task operations, durable indexed device audio uploads and prerecorded transcription. It explicitly returns unavailable for MCP, supplies unavailable accepted-work/STM coverage, persists grounded render responses and limits concurrent non-health requests to two with a 25-second deadline, extended to 135 seconds for transcription requests. It does not mount the full app-facing route set. The [GCP configuration](../backends/example-platform/deploy/gcp/dev/main.tf) targets a development project; configuration existing in the tree does not prove successful rollout, grants or authenticated app access.

Settings authority boundary: the canonical [settings projection](../backends/example-platform/apps/service/control/settings-projection.ts) requires identity and shares its entitlement projection with enforcement. Its implementations are [local SQLite](../backends/example-platform/drivers/sqlite/service-stores/settings-projection.ts) and in-memory; [app-facing producers](../backends/example-platform/apps/service/app-facing.ts) seed QA identity and optional unmetered entitlement. PostgreSQL account/grant records do not supply profile, billing or consumed usage, and [verified Firebase identity](../backends/example-platform/apps/service/auth/firebase-identity.ts) supplies only project, UID, authentication strength and expiry. A deployed settings reader needs an owner-backed profile projection and the same persisted entitlement/usage producer used by enforcement. Meanwhile, native `/v1/users/profile` and `/v1/users/me/subscription` continue through the primary cloud [client](../react-native/src/desktopCloudClient.ts) and [route policy](../react-native/src/v5BackendOrigin.ts); they are not portable-backend implementations. Web service settings read the existing local projection, preserve absent identity/entitlement, and label chat requests and transcription seconds separately. Unknown allowance units remain unavailable; this local read does not create a deployed producer.

Chat identity boundary: the PostgreSQL [memory context adapter](../backends/example-platform/drivers/postgres/firebase-chat-generation-context-source.ts) now produces the trusted context packet consumed by the current supervisor, using the authenticated account-bound memory read. This does not authorize chat generation. The unmounted [gateway source](../backends/example-platform/apps/service/chat/generation-source.ts) still sends the opaque context account ID as `x-omi-user-uid` and defaults its service caller to `platform`; neither establishes the verified Firebase UID or a gateway-allowlisted caller. Production chat must compose the actual verified Firebase identity, account binding and explicit caller configuration before mounting this source. Its PostgreSQL admission, message/event persistence and entitlement authority are also missing; the local QA principal and memory-read grant cannot substitute for them.

Chat entitlement integration prerequisite: the legacy origin owns `backend/utils/subscription.py:get_chat_quota_snapshot`, catalog revision 2 in `backend/config/plan_catalog.json`, and UTC monthly consumption in `backend/database/user_usage.py:get_monthly_chat_usage`. The `/v1/users/me/usage-quota` response is a read snapshot, not an atomic reservation; the gateway's `gateway/jit_budget.py` reservation is restricted to JIT QA run budgets and cannot authorize subscriber chat. The required source-owned admission operation must bind the verified Firebase project/UID, canonical account and epoch, client-message ID and payload hash to one durable reservation. Exact replay must return its existing receipt without consuming again; changed payload must conflict; missing source state must be unavailable; exhaustion must remain an entitlement refusal. The receipt needs the source catalog/subscription revision, UTC usage period and billing unit, and must be persisted with PostgreSQL message admission and its first generation event. Completion must settle that same reservation once from gateway-owned provider-attempt accounting; interrupted or unknown-cost attempts must not be silently released. A same-message retry after an uncertain response must reconcile the reservation rather than allocate another. These are integration requirements, not an implemented public endpoint: the legacy source producer and its authenticated transport do not yet exist. PostgreSQL `chat.read` and `chat.write` would require explicit grants through the existing application authorization lifecycle; neither Firebase identity alone nor a memory grant supplies them. The current token-only `ChatGenerationUsage` shape also lacks the cost and settlement evidence needed for monetary plans.

## Acceptance checklist for subsequent work

- [ ] **Production authority:** provision and verify real Firebase credential binding, application grant, account control and revocation for an intended account; no seeded principal or staging-token substitution.
- [ ] **Full deployed composition:** mount every required app capability above with production stores, model/storage ports and bounded shutdown/readiness behavior. Keep unsupported routes explicit until implemented.
- [ ] **Provider independence:** run the same app contract scenarios against Worker and portable production composition. Where the app wire differs (`/v1/device-sessions` versus `/v4/listen`), implement the accepted boundary rather than silently switching semantics.
- [ ] **Real mobile path:** fresh setup → sign-in → optional device → recording/transcript → conversation → task mutation → Settings/Apps, with reload and account isolation. Simulator rendering alone does not close physical-device checks.
- [ ] **Failure and recovery:** credential expiration/revocation, offline/process death, interrupted uploads, uncertain writes, SSE reconnect/cancel, stale task revision/epoch and unavailable projections produce the intended recoverable state.
- [ ] **Production release evidence:** record deployed revision/configuration, account-scoped end-to-end results, migration/rollback readiness and provider-specific resource verification. Health/ready 200 and a container image are prerequisites, not full parity.

Existing local evidence and limitations live in [production-readiness.md](production-readiness.md). This checklist adds no new domain authority, seeded production data, or declaration that all capabilities are complete.

Browser parity remains open: current browser setup continues into Omi, and Apps explains that it is not available for this browser connection yet instead of offering an unusable sign-in. These capability boundaries do not complete browser authentication, connector authorization or app installation. The browser still needs real identity/session and app-service composition before those actions can be enabled.
