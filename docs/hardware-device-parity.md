This inventory was checked against the current v5 source and the main app's `app/lib/services/devices/connectors/omi_connection.dart`, `models.dart`, device settings and firmware flows on 2026-09-07.

The main app also contains Apple Watch, OmiGlass, Ray-Ban Meta and third-party connectors. Their existence is part of the parity inventory, not proof that v5 implements them. Preserve the current product decisions and capability-specific protocols when adding support; do not label all devices supported merely because they advertise Bluetooth.

Hardware acceptance remains open until both the native path and its deployed backend are exercised. Synthetic packet, state-machine and HTTP tests are required regression coverage but cannot substitute for physical device results.

Native connection setup now has a 20-second deadline on Apple and Android. Android serial GATT operations have an 8-second deadline and retire the connection on timeout so delayed callbacks cannot acknowledge a later operation. Connection success and recording require a codec plus confirmed audio notifications. Native callbacks from retired connections are ignored, manual disconnect rejects pending setup, and Bluetooth power loss retires capture. Power restoration permits manual scanning and connection; bounded reconnect after an unexpected link loss is described below. Pure native tests cover generation/operation fencing, stale Apple peripheral callbacks, setup expiry, and recording readiness. These checks do not replace physical testing of disconnect during discovery, missing CCCD acknowledgments, and radio power cycles.

Apple retains a cancelled peripheral in quarantine until its disconnect or failure callback arrives, including across radio power changes. Reconnecting that same object before acknowledgement is rejected; a radio-on callback alone does not prove the old connection callbacks have drained. This boundary still needs physical power-cycle verification.

LED writes are one byte in the range 0–100; microphone gain is one byte in the range 0–8. These bounds come from the main firmware `omi/firmware/omi/src/lib/core/transport.c` handlers, which are stricter than the old app connector's microphone clamp. Feature bits 7 and 8 are defined in `features.h`; missing or malformed masks never enable writes. This gate matters because the settings UUID family overlaps the OmiGlass OTA family. The controls implement no firmware-update operation. A confirmed read-back reports current device state; it does not prove flash persistence or a completed physical-device acceptance test. Shared controls appear in the mobile device panel and the desktop General settings device slot.

Bounded reconnect becomes eligible only after codec and audio notifications are ready. Failed initial pairing never retries automatically; each reconnect must establish readiness again before capture resumes. The target remains visible while connecting so account-session retirement can cancel a backoff. Apple waits for the retired peripheral callback before reuse. Android, iOS and macOS builds and native policy tests passed in /tmp/omi-reconnect-*-build.log and /tmp/omi-reconnect-native-tests.log; physical link-loss and radio-cycle acceptance remain open.

Find device uses service `cab1ab95-2ea5-4f4d-bb56-874b72cfc984` and characteristic `cab1ab96-2ea5-4f4d-bb56-874b72cfc984`, requiring write-with-response support. Each command is exactly one byte, value 3 (firmware 500 ms vibration); subsequent commands wait 750 ms after acknowledgement, matching the main connector pattern. The operation shares the native device-control slot, has an 8-second write deadline, and disconnect or account retirement cancels unsent commands. The UI reports command acknowledgement, not observed vibration. Native sequence tests cover three-command bounds, duplicate acknowledgements and retired callbacks; physical-device confirmation remains required.

Android background support uses `FOREGROUND_SERVICE_CONNECTED_DEVICE` and the granted Bluetooth runtime permission. Initial connection must start with a resumed app; the existing bounded reconnect keeps its service without requesting a new background start. Disconnect, account retirement, radio loss, exhausted retries, module disposal and task removal stop the service. Android 13 notification denial can hide its notification from the drawer while the OS active-apps surface remains available; the existing permission UI remains the permission owner. See [Android BLE background guidance](https://developer.android.com/develop/connectivity/bluetooth/ble/background) and [foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types).

The iOS `bluetooth-central` declaration allows CoreBluetooth event wakeups for the existing approved connection; it does not add audio background mode, state restoration or a microphone session. Neither platform configuration proves that every event reaches React Native and the encrypted journal before suspension, nor guarantees survival after process termination. Physical capture and recovery remain required; see [Apple CoreBluetooth background guidance](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html).

Storage status targets the consumer Omi firmware (`omi/nrf5340/cpuapp`, `CONFIG_OMI_ENABLE_OFFLINE_STORAGE=y`), identified at runtime by feature bit 6 plus the readable characteristic. It does not infer support from a device name or claim support for other connector families. Source: main repository `omi/firmware/omi/README.md`, `omi.conf`, `src/lib/core/features.h` and `transport.c:486`.

The storage service is `30295780-4301-eabd-2904-2849adfeae43`. Reading `30295782-4301-eabd-2904-2849adfeae43` returns exactly four little-endian uint32 values: used bytes, unread packets, free bytes and RTC validity (0/1), in `omi/firmware/omi/src/lib/core/storage.c:605`. These are firmware-cached values, not a capacity or successful-sync guarantee. Zero reported capacity is unavailable. The legacy devkit's eight-byte file-size/offset response is rejected; the main app's small-second-field file-count heuristic is not used. Shared controls require an explicit read and retain the last-reported label, with no storage writes or notification subscription.

Full transfer has a separate ownership blocker. On the write/notify characteristic `30295781-4301-eabd-2904-2849adfeae43`, current ring commands are info `0x10`, read `0x11` + BE uint64 start sequence (+ optional BE uint32 count; 9/13 total bytes), advance `0x12` + BE uint64 sequence (9 bytes), clear `0x13`, and stop `0x03`. Info notifications contain a one-byte tag, BE uint64 read/write sequences, BE uint32 capacity, BE uint64 dropped count and BE uint16 packet size (31 bytes). Current firmware `storage_data_tx_done` (`storage.c:248`) counts bytes when BLE notification transmission completes; `sync_checkpoint_advance` (`storage.c:414`) can persist/free that range during streaming and again on stop/disconnect. This is not an application journal or backend acknowledgement. Before implementing transfer, firmware and app must establish durable-acceptance ownership; v5 must never advance, delete or clear unacknowledged audio. The older main multi-file `0x10/0x11/0x12` meanings also conflict with the current ring protocol, so command IDs alone cannot select an implementation.

Button support uses service `23ba7924-0000-1000-7450-346eac492e92` and notification characteristic `23ba7925-0000-1000-7450-346eac492e92`. Current consumer firmware `omi/firmware/omi/src/lib/core/button.c` sends two little-endian 32-bit integers: action followed by reserved zero. V5 accepts exactly eight bytes and acts only on action 2; it never replays the characteristic read value as a gesture. Feature bit 2 plus an acknowledged notification subscription gates the UI. Main app `app/lib/services/capture/capture_controller.dart` owns the default double-press conversation boundary; this slice does not infer new voice, mute or bookmark actions. Native decoder and capability-label tests and all three native builds passed (`/tmp/v5-button-native.log`, `/tmp/v5-button-ui.log`, `/tmp/v5-button-{ios,macos,android}-build.log`). No physical device button or uninterrupted recording result has been verified.

Offline capture chronology remains incomplete: the native journal input and persisted descriptor carry device identity and codec but no original capture timestamp (`react-native/src/omiNativeTypes.ts`). PostgreSQL first remote open uses server time in `createPostgresDeviceSessionUploadRepository` (`drivers/postgres/listen-finalization-repository.ts`), so a capture that never reached the server before going offline is dated at recovery. Existing successful opens replay idempotently with their original server timestamp. Preserving capture-time provenance through the journal and both backend implementations needs a coordinated wire change and regression before offline chronology can be considered complete.

Upload completion also records server time, while portable transcription derives conversation duration from decoded/provider audio. Backdating only the upload start would conflate capture time with time waiting for recovery. Device-reported capture time must remain separate from server receipt time, authorization clocks and billable decoded duration. Existing journals have neither packet timestamps nor a timed stop record; a crash-recovered journal cannot supply a known stop time. Replay time and file modification time must not be presented as original capture evidence.


First-audio readiness keeps the BLE link and recording session intact while no packets have arrived. Native code reports `audioStatus: waiting`, retries the audio notification subscription once after four seconds, then remains waiting; the first nonempty packet changes the status to active. A packet arriving before codec/notification readiness also cancels the first-audio watchdog. Connection retirement invalidates its timer. This follows main `app/lib/services/devices/transports/native_ble_transport.dart` (four-second window, one retry, no silence-triggered disconnect). Consumer firmware `omi/firmware/omi/src/mic.c` `aad_track_silence` explicitly sleeps the microphone/PDM during connected silence and resumes on sound, so silence alone is not a broken link. Actual GATT failures retain the existing failure policy. This is a first-packet check, not an ongoing audio activity meter; physical quiet-to-sound recovery remains unverified.
