# SCA-2015: ready-owner discovery cursor

The 100-oldest ready page can contain only held backlog and hide a quiet owner's ready fresh row.
Maintenance visits distinct pending ready owners in owner-key order and persists progress in `{ns}_merge_discovery/cursor` across restarts.
Each pass stores the greatest ready, merge-pending owner key as `ceiling_owner_key`; seeks stay above the cursor and at or below that ceiling. The last owner or a short seek records the wrap in the same tick; the next tick reads a new ceiling. An empty ceiling logs owners=0 wrapped=1. Arrivals behind the cursor or beyond the ceiling wait for the next pass.
`BATCH_PIPELINE_READY_DISCOVERY_OWNERS_PER_TICK` overrides the stored owner budget (default 20, clamped 1..100). `BATCH_PIPELINE_READY_DISCOVERY_TICK_SECONDS` bounds cooperative discovery work (default 10, clamped 1..60): checks between queries and drains stop further work, preserving undrained owners and logging budget_spent=1. An in-flight synchronous query or drain can overrun the deadline.
Reads per successful tick = owner seek rows + owners drained × reads per drain + 2 cursor reads + 1 ceiling read per pass, plus minimum charges for empty queries; discovery writes per accepted tick = 1 (stale pages write 0). Discovery round trips include owner seeks, one ceiling query per pass, initial cursor read, and a conditional read/write transaction, in addition to drain round trips; transaction setup and retries may add RPCs.
Without deadline clipping or changes inside the ceiling, a pass visits the owners present at its start in `max(1, ceil(O / B))` ticks, where O is their count and B the owner budget. The default maintenance cadences are 20 s for serving and 5 s for the pump, sharing one cursor, so elapsed pass time depends on their combined ticks; deadline clipping can add ticks.
The cursor uses existing merge gates: held backlog stays held while `BATCH_PIPELINE_PROVIDER_BACKLOG_RELEASE_ENABLED` is off; any owner drain can release it when that switch is on. Marker re-offer stays unchanged. Serving and pump hold separate leases and may overlap; each finish transaction compares the complete cursor snapshot and increments its `revision`, so a stale page cannot rewind progress or claim a published wrap. Duplicate drains remain transaction-fenced.
Stored-field contract: `revision` is a nonnegative integer, absent means 0, and every accepted finish increments it; malformed values use the old-page fallback without a cursor write. Writers/readers are `ReadyDiscovery` in backend-integration serving maintenance and the GKE worker pump, on Firestore/Postgres, plus the simulator. No job/result fields change. Pre-cursor code ignores this document; earlier cursor versions preserve unknown fields but write unconditionally and do not increment the revision. Stale-writer protection therefore requires every cursor writer to run the conditional version; mixed older cursor writers are not acceptance proof. The revision distinguishes repeated positions/pass timestamps across wrap and prevents an old page from replacing a new pass.
Missing owner ids are skipped while advancing, with only missing_owner_id counts logged. Cursor read/write/query failures fall back to the old page; Google API and Postgres operational errors log retry/unavailable, other errors log outcome=error at ERROR level and still fall back. FailedPrecondition backs off for 300 seconds per process.
Known limits: `0007_ready_owners.sql` follows earlier plain CREATE INDEX migrations; the runner wraps each migration in a transaction, so index creation is not online-safe for a Postgres job table under write traffic. Whether the Postgres job store serves production today: not determined. Live query/index readiness was not verified locally.
Set `BATCH_PIPELINE_READY_DISCOVERY_CURSOR_ENABLED=false` to restore the 100-oldest ready page; cursor state remains for resumption.
