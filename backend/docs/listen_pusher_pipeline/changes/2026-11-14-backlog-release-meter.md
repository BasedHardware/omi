# Metered provider backlog release

Provider backlog release previously allowed every ready held row through when its legacy release switch was true, subject to the existing catch-up depth.
The default-on `BATCH_PIPELINE_BACKLOG_RELEASE_METER_ENABLED` now requires an uncached gate read and hourly token increment inside the fresh-selection commit transaction. Fresh commits never read this document or spend tokens; provider backlog keeps capture order within its owner and still obeys catch-up depth. Missing, closed, stale (age at least 180 seconds), exhausted, out-of-reach or unreadable gates refuse backlog without a hold marker. Read failures record fallback telemetry; transaction contention propagates to the store retry. The result carries `backlog_release: true` only for a metered commit, and observed commits and bounded refusal reasons have count metrics. These process counters can undercount a lost reply or process exit; token accounting is durable.

No gate is created by this change, so deployment with both switches unset releases nothing. An operator can open `{ns}_backlog_release/gate` (for example `batch_pipeline_prod_backlog_release/gate`) with these fields: `state: "open"`, `rate_per_hour: 2`, `reach_seconds: 86400`, `window: floor(now / 3600)`, `tokens_used: 0`, `updated_at: now` (epoch seconds, float). The operator must keep `updated_at` younger than 180 seconds without resetting current-hour tokens; merge token writes preserve that heartbeat. Reach uses the admission lag's capture end, `capture_at + duration_seconds`; a reach of zero is unlimited. All six fields are required and no other field is allowed: a document that is missing one, carries an extra one, or has a negative, non-integer or non-finite value is read as closed, so a partial write cannot reset the hourly count. A job without a finite `capture_at` and a non-negative `duration_seconds` gets no token (refusal reason `job`). The budget hour is the hour of `updated_at`, the heartbeat, and never the committing process's clock: usage resets on the first commit after the heartbeat enters a new epoch hour, so a retried transaction body or a committer whose clock runs fast or slow cannot roll the hour early or move it back. A `window` ahead of the heartbeat's hour reads as closed. The 180-second age limit and the reach limit are judged at the moment the gate is read inside each transaction attempt (the drain's start time plus the time elapsed since), not at the start of the drain; the commit follows that read inside the same transaction, so the limits hold as of the read and not to the instant of commit. The heartbeat writer must therefore be a single clock. Close with `state: "closed"`, rate zero, or the legacy release switch explicitly `false`.

| Meter | Legacy provider release | Effect |
| --- | --- | --- |
| on/unset | unset/true | Gate document decides; absent means closed |
| on/unset | false | Closed regardless of document |
| false | true | Legacy unmetered behavior, including catch-up depth |
| false | unset/false | Legacy backlog hold |

This adds one transactional document read per backlog attempt and one write per released row, without cross-call caching or an index. With a ready held head and no fresh rows, the two transactions perform nine baseline document reads for a release, or seven for a gate refusal, plus up to two projection-watermark reads when depth is enabled. Those counts include minimum billing for empty fresh queries, exclude contention retries and commit-time privacy-fence reads, and exclude discovery's cursor and owner-query costs. A release writes result, job, owner and gate (four documents); a refusal writes none. An explicit false override skips the document read. A closed owner visit keeps the existing strict transaction and fresh gate queries, adding only the one document read. Collection budgets are planning bounds per environment, not measurements or enforced attempt limits.

This does not add a controller, cache, operator script, newest-first ordering, projection policy or production configuration. Before opening a gate, the rollout owner must verify the commit-gate revision on every committing service. The off switch is `BATCH_PIPELINE_BACKLOG_RELEASE_METER_ENABLED=false`; disabling the meter returns enforcement to the legacy release switch.

Readers/writers by version: this revision's `OrderedMerge` in both Cloud Run `backend-integration` and the GKE batch worker reads all six gate fields and writes only the token window/count, preserving the heartbeat. The shared Firestore, Postgres and simulator transaction adapters carry the document without a schema migration. Postgres remains dark; this change does not authorize it to serve. Older committing revisions ignore the document and follow the legacy provider release switch, so keep `BATCH_PIPELINE_PROVIDER_BACKLOG_RELEASE_ENABLED=false` on every committer throughout rollout and rollback. No heartbeat writer ships here; PR 4 must supply one fenced authority and preserve current-hour tokens transactionally. The `backlog_release` result field is written only by metered merge, read by the observed commit counter and synthetic conformance assertions; projection follows the existing predecessor/privacy fences and does not branch on it. The existing cursor, conditional revision writes, serving metric exports and migration 0007 are preserved; parking's unmerged migration 0008 is not included.
