# v3 per-owner holdout (SCA-2918)

Owners in the `conversations-v3-holdout` rollout cohort keep legacy intake for
new captures at every stage. Stage admission (`conversations_v3_enabled`) is
unchanged. `v3_intake_held_out` is asked only after it admits, and only where
new intake is decided:

- `triggers.mark_new` (listen in-progress create, sync ingest, batch projection)
  leaves new rows unmarked: the same state as an owner whose capable marker lapsed.
- Manual cuts (`record_end`, `ends_around`) behave as with the experiment off.
- Home reads legacy mode. `v3_derived` cards stay visible; `held_for_notes`
  never matches `recording` or `v3_derived` rows, so `show_held` adds only new legacy pieces.
- `/live` still serves an existing active window. It answers `v3:false` only when
  there is none.

Finish, episodes and builders keep stage admission, so stored v3 recordings
drain on the v3 path. The capture in flight when an owner is added keeps its
layer.

Membership is the existing per-uid `rollout_cohorts/{uid}` document behind the
60 s process cache. It is read only for stage-admitted owners, and by `/live`
only when no active window exists. Unknown membership admits and records a
`feature_flags` / `v3_holdout` fallback, so a cold cache can still admit a
held-out owner. `CONVERSATIONS_V3_HOLDOUT=off` skips the check and the read.
Runbook: `docs/runbooks/conversations-v3.md#per-owner-holdout`.
