Its billing table is the active resource export; do not sum the predecessor billing account or the standard export into it.

## Denominators and reconciliation

The component table reports production net billed cost, including credits, divided by 120 wall-clock hours on October 7–11. Pool costs include associated CPU, RAM, GPU, and pool-labelled charges; namespace/workload allocation is inferred from the dedicated pool's purpose. Unlabelled disks, networking, monitoring and cluster overhead are outside the component table. Audio GCS is the private-cloud-sync/syncing-local bucket family, including historical retention and operations, not the cost of storing one newly uploaded hour. Backend-sync is Cloud Run and belongs to shared allocation in the current classifier; it must not be added again to `audio_pipeline_gcp`. Listen and pusher are GKE pools in these billing rows.

The allocation code defines audio as ASR GPU fleet + audio storage + listen/pusher pool compute. It aggregates the billing account, including non-production, and allocates by transcription seconds. Therefore $0.062 is neither GPU list price nor marginal cost. The latest settled five-day allocation is $2,323.47 / 33,493.35 transcription hours = $0.069371/hour. The live classifier rerun for those same days totals $1,968.69 production + $280.87 non-production = $2,249.55, **3.18% below the persisted allocation**. This receipt does not reconcile away that difference. Possible causes include export revisions and different captured loader inputs/source; the archived loader receipt is needed to identify which. Do not present the component table as an exact decomposition of the persisted per-user rate.

The latest export has usage through October 13 23:00 UTC, but that day's charges are incomplete (for example, audio storage totals $58.74 versus roughly $180–210 on preceding days). FinOps has no October 12–14 rows. Thus there is no confirmed "today" baseline.

The five-point OLS fits daily allocated cost to transcription hours: fixed $371.88/day, slope $0.013855/hour, R²=0.726. At observed volume these contributions are $0.05552 fixed allocation and $0.01386 variable per transcription hour. Approximate classical 95% intervals (three degrees of freedom) are $265–478/day for the intercept and −$0.0018 to $0.0295/hour for the slope. Neither is a causal marginal-cost estimate. The 120-point hourly production-pool-plus-storage fit to listen connections has R²=0.000002, slope −$0.000261/stream-hour with SE $0.016714. Metering bursts, storage stock, hourly snapshot error, and workload mix prevent identification. No reliable economic fixed/elastic split is measured here.

## Fleet and latency

DCGM uses one-hour averages, deduplicated by GPU UUID before pool averaging. Each active GPU pool has 168 hourly utilization/memory observations. Node counts use deduplicated `kube_node_info`, with 167 snapshots; GPU coverage counts use instantaneous DCGM. `kube_node_labels` is absent, so historical pool identity comes from GKE node-name prefixes. NLLB's prefix is truncated to `nllb-translation-poo`; Parakeet names remain distinct. The B pool's historical four-node observation exceeds its current maximum of three; this can reflect an earlier configuration or a rolling surge and is not a request to raise the limit. Absent `minNodeCount` is zero; each GPU pool has one configured zone, so these are per-zone and total limits. Old VAD and engine pools have no sampled nodes or billed pool rows in this production window; that is not proof they can be deleted.

Hourly mean GPU utilization peaks: Parakeet A/B 13.1%/16.0%, NLLB 23.4%, VAD 30.9%, diarizer 21.3%. Instantaneous utilization can spike far above these means. Memory numbers are used MiB / 1024, not CUDA-only peaks. Current HPA specs and node-pool configuration are recorded in the local receipt. Current VAD/diarizer HPA latency metrics are the internal-LB p99 histogram, with 2000/300 millisecond targets.

Window POST p95 averages 1.05 seconds, with maximum hourly p95 1.47 seconds. First-text p95 averages 18.69 seconds and reaches 60 seconds; it includes window/capture waiting and is not interchangeable with POST latency. These observations **do not satisfy a new admission qualification**. ## Batch model and policy qualification

Parakeet source records audio duration for v1/v2 POSTs, and service elapsed time in endpoint-labelled request histograms. Prometheus scrapes overwrite `endpoint` with `metrics`; application labels become `exported_endpoint`. The measured seven-day service-time/audio ratio at the last observation is 0.033072; it includes short live-window requests, queueing and postprocessing. It is a conservative **proxy estimate**, not a dedicated long-file GPU benchmark or a measured batch RTF. Errors can inflate the numerator; batching can overlap request times. Qualify public audio batch throughput before committing capacity. ASR RTF sensitivity 0.01–0.10 gives total batch cost about $0.0344–0.1112/full-speech worn-hour with pyannote fixed at 0.03.

Pyannote's supplied Sol receipt (`sol-final-pass-result.md`, lead workspace) reports public AMI RTF 0.02953–0.03138 on a shared dev L4, device peak 6.312 GiB; Python 3.12 differs from shipping 3.11. No benchmark is rerun here.

The modeled G2/L4 whole-node on-demand rate is $0.853624312/hour ([Google pricing](https://cloud.google.com/products/compute/pricing/accelerator-optimized)). At 24 kbps, one hour is 10.8 MB = 0.010058 GiB. Thirty days in single-region Standard storage costs about $0.000201/hour uploaded, plus $0.000005 for one Class A PUT; ingress is free ([GCS pricing](https://cloud.google.com/storage/pricing)). This is a new regional-Standard retention scenario, not the existing bucket's lifecycle. Costs scale with retained speech fraction only if VAD suppresses uploads too. Packaging thousands of small objects, Coldline retrieval, replication, cross-region transfer, decoding/orchestration, and retries add costs. GPU residency and idle floors are separate; at utilization u, compute allocation is divided by u.

Propose retaining current 35% Parakeet GPU scaling as a secondary guard and trialing the request/queue target above the current two requests only after qualification. Use the peak arrival/workload envelope and qualified per-replica capacity to set an N+1 floor (at least three across the existing two zones); retain seven as the initial ceiling. Scale up before queue latency breaches the budget, stabilize down 900 seconds, and drain live sessions before terminating a replica. Do not use total listen connections as Parakeet demand: provider mix differs, and the native stream gauge is near zero because windowed POST traffic dominates.

NLLB: keep one replica, maximum two; trial queue-age/GPU scaling rather than CPU-only 70%, with translation p95 regression guard. VAD: keep one, maximum ten and the current two-second p99 guard; combine queue age with measured GPU load. Diarizer: keep one, maximum ten and its 300ms p99 guard; qualify queue-based scaling and 900-second scale-down. Numerical GPU targets for these three pools require workload qualification; no savings from lowering their one-node floor are credited.

Batch can consume idle *time* through an admission-aware worker lane that yields to live requests; reserve measured memory and bound non-preemptible inference chunks. Kubernetes PriorityClass does not share a fully requested GPU between pods and cannot preempt a CUDA kernel inside a live process. Separate batch pods can consume spare *nodes* at lower priority and be preempted; checkpointed, idempotent batch can instead use a separate spot L4 pool. Spot capacity and price are not assumed.

The seven-day live node mean is about 6.25. A qualified policy holding 4–5 nodes on average removes roughly 1.25–2.25 node-days/day. The settled net Parakeet rate is about $0.62/node-hour, yielding an **$18–33/day allocated run-rate reduction**. This scenario is low-confidence and may fail the p95/availability gate. It is not a promised cash saving: committed-use obligations, unused credits, idle batch consumption, model warm-up, and buffer requirements can reduce savings to zero. No extra batch savings are added to the same removed node capacity.
