# CV1 BLE central (macOS)

Small Swift/AppKit/CoreBluetooth app for explicitly authorized bench runs. Building and pure tests never initialize Bluetooth. Requires macOS 13+ and an existing Swift/Xcode toolchain; the intended bench host runs macOS 27. No package installation or network code is included. SMP image upload, image state writes, and OS reset are device mutations that need a **per-run bench authorization**. Audio and SMP commands also enable/disable notifications (CCC subscription). Bonds and pairing are still never used; no pairing APIs are included. Session/audio refuse required characteristics without `read`, or audio without `notify`; there is no write-based enable/unlock fallback. Protected-read errors fail without a retry. CoreBluetooth does not expose attribute security permissions ahead of a read; these commands target the candidate firmware's unencrypted read/notify services, not arbitrary secured peripherals.

## Build and offline tests

From the monorepo root:

```sh
omi/firmware/tools/cv1/ble_central/test.sh
omi/firmware/tools/cv1/ble_central/build.sh /path/to/new/CV1BLECentral.app
python3 -m unittest discover -s omi/firmware/tools/cv1 -p test_ble_central.py -v
python3 omi/firmware/tools/cv1/ble_central/check_rejections.py /path/to/new/CV1BLECentral.app/Contents/MacOS/CV1BLECentral
```

The app destination and its parent must be chosen deliberately: the parent must exist and the destination must be new. The build compiles Swift, copies `Info.plist` with `NSBluetoothAlwaysUsageDescription`, ad-hoc signs the entire bundle, and verifies its signature. It never launches it. No signing identity or credential is used. Keep the bundle in a stable location for macOS permission attribution; rebuilding ad-hoc code may require renewed consent. Pure tests link Foundation only. The optional Python discovery entrypoint skips if Swift is unavailable, including an unconfigured toolchain shim. `check_rejections.py` invokes only invalid-argument/file-collision paths that exit before AppKit or any Bluetooth object is initialized; it never exercises a valid scan/session.

## Authorized live use only

No real scan is approved by adding or testing this tool. After obtaining bench authorization, launch the signed app bundle through Launch Services with `open -n -W`, as the logged-in console user. From an SSH session, use that same user, with the console available to approve the normal Bluetooth permission prompt. Direct execution from an SSH shell may attribute the Bluetooth request to `sshd` and deny it without showing this app's prompt. Do not run the bundle executable directly for live use, run through `swift`, copy out the executable, use `sudo`, change TCC, or bypass the prompt. This is a real `APPL` bundle using the AppKit event loop; the intended Launch Services permission attribution has **not been verified live**. The permission wait counts against the deadline; rerun explicitly with a new receipt after granting permission if necessary. There is no automatic relaunch or retry. `open -n -W` waits for the app to exit but does not capture its stdout or convey its bench outcome: read the JSON at `--output` and inspect `outcome`.

```sh
open -n -W /path/CV1BLECentral.app --args scan --seconds 10 --name-prefix Omi --output /path/to/new-scan.json
open -n -W /path/CV1BLECentral.app --args session --seconds 20 --output /path/to/new-session.json
open -n -W /path/CV1BLECentral.app --args session --seconds 20 --expect-serial EXPECTED_SERIAL --output /path/to/new-identified-session.json
open -n -W /path/CV1BLECentral.app --args audio --seconds 3 --expect-serial EXPECTED_SERIAL --output /path/to/new-audio.json
cat /path/to/new-audio.json
```

All commands require `--seconds` and `--output`. Names match a case-insensitive advertisement-local-name prefix (default `Omi`); nameless and unrelated advertisements are discarded. Scan receipts report name, RSSI, advertised/overflow services, and connectability, retaining up to 512 advertisements and counting omitted ones. They contain no CoreBluetooth peripheral identifiers or unrelated manufacturer data. Scan never connects. Every other receipt records the connected peripheral's CoreBluetooth identifier as `peripheralIdentifier`; it is per-host and private like the serial. Session/audio and both image commands select the first matching advertisement and stop scanning; a name match does not identify the intended pendant. Session and image-state accept `--expect-serial VALUE` or `--expect-peripheral UUID`; audio and image-upload require one of them, and refuse missing/empty/invalid values as invalid arguments before creating a receipt or initializing Bluetooth. Scan rejects both options. Replace `EXPECTED_SERIAL` in the examples with the intended unit's serial, obtained independently; it is not a literal serial. The expected and observed serials stay in the private local receipt; don't commit receipts or captures to this public repository.

Session connects once, enumerates service UUIDs, discovers only allowlisted characteristics, and reads required DIS firmware revision (`180A/2A26`) followed by serial (`180A/2A25`) if present. Serial is optional, alongside features and diagnostics: missing serial on the baseline 3.0.21 control image is recorded in `absentOptionalCharacteristics` and does not fail a session without `--expect-serial`. With `--expect-serial`, the first connection checks the DIS serial before features/diagnostics, any reconnect or notification subscription. A missing, empty, non-UTF-8 or different value immediately stops with `gatt_failed` and a detail saying the serial was absent or wrong. Comparison is case-sensitive and does not trim whitespace. The receipt's `identity` contains `expectedSerial` when requested, `checked`, and status `not_requested`, `pending`, `matched`, `absent`, or `wrong`; a run that fails before the comparison remains unchecked. This gate does not prevent the initial connection or DIS reads, and a session without the option does not establish identity.

After DIS and any requested identity check pass, session reads features/diagnostics if present. An absent optional characteristic is recorded; an error reading one that exists fails GATT. It disconnects, waits for acknowledgment, reconnects to the same in-memory peripheral exactly once, rediscovers, reads firmware revision again, and disconnects. No failed operation is retried and no alternate name-matched target is tried after an identity failure. Each connection records firmware text/raw hex and observed `maximumWriteValueLength` with/without response, without sending a write. **CoreBluetooth exposes neither raw ATT MTU nor individual long-read offsets.** These maximum write lengths are API observations, not reconstructed MTU or evidence of offset-read correctness.

Audio performs the complete session and one reconnect, then subscribes on that second connection, collects notifications for `--seconds` (strictly >0 and <=3), unsubscribes, waits for acknowledgment, and disconnects. It counts notification packets, all bytes, payload bytes, and frame starts, and checks packet-sequence and fragment continuity. Zero notifications, malformed packets, discontinuities, subscription/unsubscription failures or missing final disconnect fail audio. Audio is discarded unless `--keep-audio /path/to/new.bin` is supplied; that path must also be new. The local binary format is repeated `[uint32 little-endian notification length][original notification bytes]`, capped at 4 MiB. It contains compressed payload, not a WAV file. Nothing is uploaded.

Scan/session/image-state accept >0 to 120 seconds as an overall deadline, including permission/setup/cleanup. Audio permits 30 seconds for session/setup, up to 3 seconds for capture, and 2 seconds for unsubscribe/disconnect. Image-upload accepts >0 to 3600 seconds as its overall deadline, including upload, reset, reconnect and cleanup. A main-loop deadline stops activity; an independent watchdog exits no later than one additional second if callbacks or the main loop stall. Failures/deadlines request unsubscribe/disconnect without awaiting acknowledgments, then exit; receipts distinguish requested cleanup from acknowledged cleanup. A process exit drops its CoreBluetooth connection. Normal success requires the specified cleanup acknowledgments. OS scheduling, suspension, forced termination and local filesystem failures cannot provide a real-time or durable-receipt guarantee.

Each valid invocation exclusively reserves one mode-0600 receipt before constructing a Bluetooth object, finalizes one JSON document, and prints its path to stdout. Exit is 0 for `passed`, 1 for a bench failure, 2 for invalid arguments or local receipt I/O failure. Invalid arguments (including audio >3), missing output parents, and existing files/symlinks are refused before Bluetooth initialization and do not overwrite or create a receipt. An existing or unopenable `--keep-audio` path is different: the receipt is still created and finalized as `audio_failed`, exit 1, also before Bluetooth initialization. A reserved receipt can remain empty if the process is forcibly killed. Keep output on a local filesystem.

The exact outcome vocabulary is `permission_denied`, `bluetooth_off`, `no_advertisement`, `connect_failed`, `gatt_failed`, `audio_failed`, `interrupted`, `passed`. Pending/denied consent at the deadline is `permission_denied`; an unavailable/unsupported adapter is `bluetooth_off`. A signal or an ended run loop is `interrupted`, whatever the run had reached. No matching advertisement remains `no_advertisement`; a selected target that cannot connect/reconnect is `connect_failed`; discovery/read/session/SMP deadlines and protocol errors are `gatt_failed`; capture-stage failures are `audio_failed`. A weak-signal board with no antenna must not be diagnosed from `no_advertisement` as if GATT had failed. Receipt stage, details and acknowledgments explain where a run stopped.

## SMP image commands (authorized bench only)

These commands select the first matching advertisement. A name prefix does not establish device identity: several pendants may share it. `image-upload` therefore requires `--expect-serial VALUE` or `--expect-peripheral UUID` before a receipt or Bluetooth object exists; `image-state` accepts either optionally. Images without a DIS serial, such as the fielded 3.0.21, can only be pinned by peripheral: learn the unit's identifier from the `peripheralIdentifier` of a serial-matched receipt on the same host, then pass it. A pinned run ignores every other advertisement (not recorded or counted), so it never connects to another pendant; the identifier is re-checked on each connection. With both options, the serial must also match. Audio accepts the same alternative. Both commands read DIS firmware revision, then serial if present, before subscribing to SMP or planning any SMP request. With an expected serial, a missing, empty, non-UTF-8 or different serial stops as `gatt_failed` with no SMP subscription or requests. Comparison uses the existing case-sensitive, no-trimming identity semantics. No alternate matching pendant is tried. Obtain per-run bench authorization before either command. Bonds and pairing are never used. No live Bluetooth or reset was used to validate this implementation.

```sh
open -n -W /path/CV1BLECentral.app --args image-state --seconds 30 --output /path/to/new-state.json
open -n -W /path/CV1BLECentral.app --args image-upload --file /path/signed.bin --expect-serial EXPECTED_SERIAL --seconds 600 --mode test --output /path/to/new-upload.json
open -n -W /path/CV1BLECentral.app --args image-upload --file /path/signed.bin --expect-serial EXPECTED_SERIAL --seconds 600 --mode confirm --no-reset --name-prefix Omi --output /path/to/new-confirm.json
```

`image-state` discovers Device Information (`180A`, firmware `2A26`, serial `2A25`) and SMP service `8D53DC1D-1DB7-4CD3-868B-8A527460AA84` and characteristic `DA2E7828-FBCE-4E01-AE9E-261174997C48`. Both write without response and notify properties are required on the SMP characteristic. DIS firmware is required and recorded under each connection's `reads`; serial may be absent only when no serial was expected. All available DIS reads and any identity check must finish before subscription. After subscription acknowledgment it sends OS bootloader info (read, group 0/id 8, empty map), image state (read, group 1/id 0), and OS echo (write, group 0/id 0). It unsubscribes and requires disconnect acknowledgment before passing.

`image-upload` requires `--expect-serial VALUE`, a readable MCUboot-signed binary and explicit `--mode test|confirm`. Local parsing requires the MCUboot header and a single 32-byte SHA256 TLV (tag `0x10`), skipping the protected TLV area when present; it does not verify the signature. A raw application binary, ZIP, or missing hash is refused before any receipt/Bluetooth initialization. The supplied file is read once. Its whole-file SHA256 is used for upload-session `sha`; the distinct image SHA256 from the TLV is used for the image state write's `hash`.

After DIS and the required identity check, the sequence is image state read → image 0 upload (write, group 1/id 1) → image state write (`hash`, `confirm` true for confirm mode, false for test) → image state read → OS reset (write, group 0/id 5). `--no-reset` ends after the second state read and acknowledged unsubscribe/disconnect. Otherwise a successful reset response must precede a device disconnect. After a one-second reboot delay the tool reconnects to that same in-memory peripheral once, rereads DIS firmware and serial and repeats the identity check before subscribing again, reads bootloader info and image state, sends echo, then unsubscribes/disconnects. All steps share the overall deadline; missing reset responses/disconnects and reconnect failures fail the run. No alternate target or failed-operation retry is attempted. `passed` proves the SMP exchange and cleanup completed, **not** that MCUboot installed the image; compare the recorded slots/hashes before and after reset. Overwrite-only MCUboot may reject test semantics or expose different pending/permanent flags: the tool records the firmware response and never substitutes confirm mode.

All requests use SMP v2 (version field `01`, 8-byte big-endian header), with one request outstanding. Upload data is chosen from the observed `maximumWriteValueLength(for: .withoutResponse)` and CBOR overhead to fit whole BLE writes within the firmware's 2475-byte reassembly buffer (including the SMP header). Requests are fragmented into writes no larger than the observed maximum, honoring `canSendWriteWithoutResponse` and the ready callback. First offset-zero chunks include `image`, `len`, `off`, whole-file `sha`, and `data`; later chunks include `off` and `data`. The next offset comes exclusively from the response's `off`, including resume/rewind offsets. Missing, unchanged or out-of-file offsets fail. Response notifications are reassembled by SMP length, and op/group/id/sequence must match. There is no resume cache or automatic retransmission; deadlines bound repeated server rewinds.

The receipt's `smp` list records ordered, timestamped request summaries (payload byte count rather than image bytes) and every decoded response, including unmatched responses before refusal. Response byte strings, including image hashes, are lowercase hex. Maps/arrays retain all supplied fields, including slot, version, bootable/pending/confirmed/active/permanent flags, `rc`, and `err`; absent flags are not invented. Nonzero `rc` or `err.rc` fails with request group/id/rc in the detail, after retaining the response. Unknown/unsupported CBOR or malformed/unmatched frames fail as `gatt_failed`. `postResetFirmware` records the reread DIS firmware revision as text/raw hex; the post-reset image state remains in `smp`. `resetRequested` and `postResetStateRead` distinguish a requested reset from a completed post-reset observation. No file names/paths or image payload are copied into SMP records.

Protocol references: [Zephyr SMP framing and errors](https://docs.zephyrproject.org/3.7.0/services/device_mgmt/smp_protocol.html), [MCUboot image/TLV layout](https://docs.mcuboot.com/design.html). Assumptions needing live bench verification: firmware enables OS bootloader info/echo/reset; its reset response precedes disconnect; a one-second delay permits the single reconnect; and its SMP netbuf can hold a 2475-byte frame. Unsupported commands fail visibly. SMP response CBOR supports definite strings and definite/indefinite maps/arrays, unsigned/negative integers and booleans; tags, floats and indefinite strings are refused.

## Wire sources and limits

Read from `origin/fw/cv1-release-candidate`, commit `2810eaf332c50e4c9a6b72d1a1f9c2838e754371` (layout source, not a claim about connected firmware):

- `omi/firmware/docs/gatt-map.md`: base suffix `-E8F2-537E-4F6C-D104768A1214`, audio `19B10000/01`, features `19B10020/21`, diagnostics `19B10040/41`, safe-mode recovery state `19B10042` (read as raw bytes).
- `omi/firmware/omi/src/lib/core/transport.c`, `push_to_gatt`: three-byte header `[sequence low, sequence high, fragment index]`; `packet_next_index` is a `uint16_t` incremented per notification, and fragment index restarts at zero for each encoded frame. Wrap at 65535 is valid. First packet/fragment may begin mid-stream. Fragment zero counts frame starts; there is no final-fragment bit, so complete decoded audio-frame counts cannot be established. No codec or audio-content decoding is attempted.
- `transport.c`, `features_read_handler`: four-byte native nRF5340 little-endian feature mask; preserved as raw hex and decoded uint32, without inventing unknown feature meanings.
- `omi/firmware/omi/src/diagnostics.h` and `diagnostics_packet.c`: exactly 25 bytes. Version at 0 (1), reset cause u32 LE at 1, uptime seconds u32 LE at 5, battery mV u16 LE at 9, charging u8 at 11, reserved zero at 12, mic-overrun u32 LE at 13, BLE-TX-drop u32 LE at 17, storage-error u32 LE at 21.

Unknown diagnostic versions/reserved flags/lengths or feature lengths retain raw bytes with `unknown; raw bytes only`. Short or empty audio payloads fail rather than guessing a header. Pure tests establish these parsing/counting/outcome rules with synthetic bytes. Permission attribution, radio range, actual reads, reconnect behavior and notification delivery require a separately authorized live bench run and have not been established by the offline checks.
