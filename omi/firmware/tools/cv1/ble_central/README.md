# CV1 BLE central (macOS)

Small Swift/AppKit/CoreBluetooth app for explicitly authorized bench runs. Building and pure tests never initialize Bluetooth. Requires macOS 13+ and an existing Swift/Xcode toolchain; the intended bench host runs macOS 27. No package installation, network code, DFU, SMP, device writes or pairing APIs are included. The only device mutation is audio notification enable/disable (CCC subscription). A required characteristic without `read`, or audio without `notify`, is refused; there is no write-based enable/unlock fallback. Protected-read errors fail without a retry. CoreBluetooth does not expose attribute security permissions ahead of a read; these commands target the candidate firmware's unencrypted read/notify services, not arbitrary secured peripherals.

## Build and offline tests

From the monorepo root:

```sh
omi/firmware/tools/cv1/ble_central/test.sh
omi/firmware/tools/cv1/ble_central/build.sh /path/to/new/CV1BLECentral.app
python3 -m unittest discover -s omi/firmware/tools/cv1 -p test_ble_central.py -v
python3 omi/firmware/tools/cv1/ble_central/check_rejections.py /path/to/new/CV1BLECentral.app/Contents/MacOS/CV1BLECentral
```

The app destination and its parent must be chosen deliberately: the parent must exist and the destination must be new. The build compiles Swift, copies `Info.plist` with `NSBluetoothAlwaysUsageDescription`, ad-hoc signs the entire bundle, and verifies its signature. It never launches it. No signing identity or credential is used. Keep the bundle in a stable location for macOS permission attribution; rebuilding ad-hoc code may require renewed consent. Pure tests link Foundation only. The optional Python discovery entrypoint skips if Swift is unavailable, including an unconfigured toolchain shim. `check_rejections.py` invokes only invalid-argument/file-collision paths that exit before AppKit or any Bluetooth object is initialized; it never exercises a valid scan/session.

## Authorized live use only

No real scan is approved by adding or testing this tool. After obtaining bench authorization, launch the signed app bundle through Launch Services with `open -n -W`, as the logged-in console user. From an SSH session, use that same user, with the console available to approve the normal Bluetooth permission prompt. Direct execution from an SSH shell may attribute the Bluetooth request to `sshd` and deny it without showing this app's prompt. Do not run the bundle executable directly for live use, run through `swift`, copy out the executable, use `sudo`, change TCC, or bypass the prompt. This is a real `APPL` bundle using the AppKit event loop; the intended Launch Services permission attribution has **not been verified live**. The permission wait counts against the deadline; rerun explicitly with a new receipt after granting permission if necessary. There is no automatic relaunch or retry. `open -n -W` waits for the app to exit but does not capture its stdout or convey its bench outcome: read the JSON at `--output` and inspect `outcome`.

```sh
open -n -W /path/CV1BLECentral.app --args scan --seconds 10 --name-prefix Omi --output /path/to/new-scan.json
open -n -W /path/CV1BLECentral.app --args session --seconds 20 --output /path/to/new-session.json
open -n -W /path/CV1BLECentral.app --args session --seconds 20 --expect-serial EXPECTED_SERIAL --output /path/to/new-identified-session.json
open -n -W /path/CV1BLECentral.app --args audio --seconds 3 --expect-serial EXPECTED_SERIAL --output /path/to/new-audio.json
cat /path/to/new-audio.json
```

All commands require `--seconds` and `--output`. Names match a case-insensitive advertisement-local-name prefix (default `Omi`); nameless and unrelated advertisements are discarded. Scan receipts report name, RSSI, advertised/overflow services, and connectability, retaining up to 512 advertisements and counting omitted ones. They contain no CoreBluetooth peripheral identifiers or unrelated manufacturer data. Scan never connects. Session/audio select the first matching advertisement and stop scanning; a name match does not identify the intended pendant. Session accepts `--expect-serial VALUE`; audio requires it, and refuses missing/empty values as invalid arguments before creating a receipt or initializing Bluetooth. Scan rejects this option. Replace `EXPECTED_SERIAL` in the examples with the intended unit's serial, obtained independently; it is not a literal serial. The expected and observed serials stay in the private local receipt; don't commit receipts or captures to this public repository.

Session connects once, enumerates service UUIDs, discovers only allowlisted characteristics, and reads required DIS firmware revision (`180A/2A26`) followed by serial (`180A/2A25`) if present. Serial is optional, alongside features and diagnostics: missing serial on the baseline 3.0.21 control image is recorded in `absentOptionalCharacteristics` and does not fail a session without `--expect-serial`. With `--expect-serial`, the first connection checks the DIS serial before features/diagnostics, any reconnect or notification subscription. A missing, empty, non-UTF-8 or different value immediately stops with `gatt_failed` and a detail saying the serial was absent or wrong. Comparison is case-sensitive and does not trim whitespace. The receipt's `identity` contains `expectedSerial` when requested, `checked`, and status `not_requested`, `pending`, `matched`, `absent`, or `wrong`; a run that fails before the comparison remains unchecked. This gate does not prevent the initial connection or DIS reads, and a session without the option does not establish identity.

After DIS and any requested identity check pass, session reads features/diagnostics if present. An absent optional characteristic is recorded; an error reading one that exists fails GATT. It disconnects, waits for acknowledgment, reconnects to the same in-memory peripheral exactly once, rediscovers, reads firmware revision again, and disconnects. No failed operation is retried and no alternate name-matched target is tried after an identity failure. Each connection records firmware text/raw hex and observed `maximumWriteValueLength` with/without response, without sending a write. **CoreBluetooth exposes neither raw ATT MTU nor individual long-read offsets.** These maximum write lengths are API observations, not reconstructed MTU or evidence of offset-read correctness.

Audio performs the complete session and one reconnect, then subscribes on that second connection, collects notifications for `--seconds` (strictly >0 and <=3), unsubscribes, waits for acknowledgment, and disconnects. It counts notification packets, all bytes, payload bytes, and frame starts, and checks packet-sequence and fragment continuity. Zero notifications, malformed packets, discontinuities, subscription/unsubscription failures or missing final disconnect fail audio. Audio is discarded unless `--keep-audio /path/to/new.bin` is supplied; that path must also be new. The local binary format is repeated `[uint32 little-endian notification length][original notification bytes]`, capped at 4 MiB. It contains compressed payload, not a WAV file. Nothing is uploaded.

Scan/session accept >0 to 120 seconds as an overall deadline, including permission/setup/cleanup. Audio permits 30 seconds for session/setup, up to 3 seconds for capture, and 2 seconds for unsubscribe/disconnect. A main-loop deadline stops activity; an independent watchdog exits no later than one additional second if callbacks or the main loop stall. Failures/deadlines request unsubscribe/disconnect without awaiting acknowledgments, then exit; receipts distinguish requested cleanup from acknowledged cleanup. A process exit drops its CoreBluetooth connection. Normal success requires the specified cleanup acknowledgments. OS scheduling, suspension, forced termination and local filesystem failures cannot provide a real-time or durable-receipt guarantee.

Each valid invocation exclusively reserves one mode-0600 receipt before constructing a Bluetooth object, finalizes one JSON document, and prints its path to stdout. Exit is 0 for `passed`, 1 for a bench failure, 2 for invalid arguments or local receipt I/O failure. Invalid arguments (including audio >3), missing output parents, and existing files/symlinks are refused before Bluetooth initialization and do not overwrite or create a receipt. An existing or unopenable `--keep-audio` path is different: the receipt is still created and finalized as `audio_failed`, exit 1, also before Bluetooth initialization. A reserved receipt can remain empty if the process is forcibly killed. Keep output on a local filesystem.

The exact outcome vocabulary is `permission_denied`, `bluetooth_off`, `no_advertisement`, `connect_failed`, `gatt_failed`, `audio_failed`, `interrupted`, `passed`. Pending/denied consent at the deadline is `permission_denied`; an unavailable/unsupported adapter is `bluetooth_off`. A signal or an ended run loop is `interrupted`, whatever the run had reached. No matching advertisement remains `no_advertisement`; a selected target that cannot connect/reconnect is `connect_failed`; discovery/read/session deadlines are `gatt_failed`; capture-stage failures are `audio_failed`. A weak-signal board with no antenna must not be diagnosed from `no_advertisement` as if GATT had failed. Receipt stage, details and acknowledgments explain where a run stopped.

## Wire sources and limits

Read from `origin/fw/cv1-release-candidate`, commit `2810eaf332c50e4c9a6b72d1a1f9c2838e754371` (layout source, not a claim about connected firmware):

- `omi/firmware/docs/gatt-map.md`: base suffix `-E8F2-537E-4F6C-D104768A1214`, audio `19B10000/01`, features `19B10020/21`, diagnostics `19B10040/41`, safe-mode recovery state `19B10042` (read as raw bytes).
- `omi/firmware/omi/src/lib/core/transport.c`, `push_to_gatt`: three-byte header `[sequence low, sequence high, fragment index]`; `packet_next_index` is a `uint16_t` incremented per notification, and fragment index restarts at zero for each encoded frame. Wrap at 65535 is valid. First packet/fragment may begin mid-stream. Fragment zero counts frame starts; there is no final-fragment bit, so complete decoded audio-frame counts cannot be established. No codec or audio-content decoding is attempted.
- `transport.c`, `features_read_handler`: four-byte native nRF5340 little-endian feature mask; preserved as raw hex and decoded uint32, without inventing unknown feature meanings.
- `omi/firmware/omi/src/diagnostics.h` and `diagnostics_packet.c`: exactly 25 bytes. Version at 0 (1), reset cause u32 LE at 1, uptime seconds u32 LE at 5, battery mV u16 LE at 9, charging u8 at 11, reserved zero at 12, mic-overrun u32 LE at 13, BLE-TX-drop u32 LE at 17, storage-error u32 LE at 21.

Unknown diagnostic versions/reserved flags/lengths or feature lengths retain raw bytes with `unknown; raw bytes only`. Short or empty audio payloads fail rather than guessing a header. Pure tests establish these parsing/counting/outcome rules with synthetic bytes. Permission attribution, radio range, actual reads, reconnect behavior and notification delivery require a separately authorized live bench run and have not been established by the offline checks.
